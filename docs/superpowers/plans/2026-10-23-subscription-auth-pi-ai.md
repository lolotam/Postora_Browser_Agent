Spec: `docs/superpowers/specs/2026-10-23-subscription-auth-pi-ai-design.md`.
Branch: `claude/reset-main-to-local-bf1f21` (the worktree's branch; the PR says so).

## Global constraints

1. Plain JavaScript ES modules, no framework, no TypeScript. Match the surrounding
   code: short header comment per file, JSDoc on exported functions, same naming.
2. The only build step is `npm run build:vendor`, which writes `src/vendor/pi-oauth.js`.
   The extension must load unpacked from the repository with no other step.
3. pi-ai is used for OAuth login and refresh only. No model call goes through pi-ai.
4. Refresh runs only in the service worker, single-flight per provider, at least
   10 minutes before expiry, bounded by a timeout and an `AbortSignal`, with the
   worker kept alive until the result is stored. The rotated refresh token is written
   to `chrome.storage.local` before the new credential is returned, and only if the
   stored record is still the one that was refreshed (compare-and-set, see task 2).
5. Never log, post to the panel, or put in an error message any token, refresh
   token, API key, PKCE verifier, authorization URL (`auth_url`) or authorization
   code. (The Claude authorization URL carries the PKCE verifier in `state` — pi-ai
   `auth/oauth/anthropic.js:182` — so the worker opens it and the panel never sees it.
   A device-code verification URL and user code carry no secret and are shown in the
   panel; see task 3.)
6. A ChatGPT user signed in before this change stays signed in after it (migration
   of `chatgptAuth`).
7. Every user-visible string goes through `src/sidepanel/messages.js` in English and
   Arabic.
8. `npm test` passes. New behaviour has unit tests under `test/` using `node --test`,
   with `chrome.storage` and `fetch` faked as the existing tests do. Existing tests
   that exercise replaced code are updated, not deleted, unless the behaviour is gone.
9. No new runtime dependency. `esbuild` and `@earendil-works/pi-ai` are exact-pinned
   devDependencies (already added: `esbuild@0.25.11`, `@earendil-works/pi-ai@1.1.0`).
10. The implementer does not commit, push, or edit files outside the task list.

### 2. Account credential store — `src/providers/account-auth.js`

- `ACCOUNT_PROVIDERS = { chatgpt, claude, grok }` mapping to the pi-ai flow
  (`openaiCodexOAuth`, `anthropicOAuth`, `xaiOAuth`) and a label.
- **One storage key per provider**: `accountAuth.chatgpt`, `accountAuth.claude`,
  `accountAuth.grok` (literal key names), each `{ generation, credential }` where
  `credential` is pi-ai's `{ type: 'oauth', access, refresh, expires, ...extra }`.
  Separate keys mean two providers never overwrite each other's record.
- Every write for one provider goes through one per-provider serial queue (a
  promise chain): migration, store after login, refresh, import, sign-out.
- **Generation**: sign-in and sign-out increment `generation`. A refresh records the
  generation and refresh token it started from and stores its result only if both
  still match; otherwise the result is dropped. A refresh failure deletes the record
  only under the same condition. A login stores only if it is still the current
  login attempt for that provider (attempt id from task 3) **and** the generation is
  unchanged since the attempt started. `signOut` and `auth-import` also cancel the
  provider's running attempt, so its result can never overwrite them.
- **Validate every credential before storing it** (after login and after refresh):
  `access` and `refresh` are non-empty strings and `expires` is a finite number in
  the future. pi-ai's Anthropic refresh resolves `{}` from an HTTP 200 into undefined
  tokens and a `NaN` expiry (`auth/oauth/anthropic.js:220-229`); such a result keeps
  the previous record and raises a retryable error.
- API: `readCredential`, `getValidCredential(provider, { forceRefresh, signal })`,
  `accountStatus(provider)` (connected, email/plan where known, `expires`),
  `signOut(provider)`, `storeCredential(provider, credential, { attemptId })`.
- Migration of legacy `chatgptAuth`
  (`accessToken→access`, `refreshToken→refresh`, `expiresAt→expires`, keep
  `accountId`, `email`, `planType`, `idToken`) into `accountAuth.chatgpt`, then
  remove `chatgptAuth` — inside the chatgpt queue, idempotent.
- Refresh per global constraint 4, calling `flow.refresh(credential, signal)` with a
  30 s timeout. **Error policy**: delete the record only on a confirmed OAuth
  rejection — HTTP 400/401/403 whose body or message carries `invalid_grant`,
  `invalid_client`, `unauthorized_client` or `invalid_token` (parse what pi-ai's
  thrown messages actually contain; tests use those real shapes). Cancellation,
  timeouts, network errors, 408/429/5xx, malformed responses and anything
  unclassified keep the record and throw a retryable error. The upstream text is
  never shown.
- The flow functions are injectable (`setAccountFlows` for tests), defaulting to
  `src/vendor/pi-oauth.js`.
- `test/account-auth.test.js`: migration (idempotent); refresh at 10 minutes and not
  at 11; single-flight per provider; two providers refreshing concurrently both keep
  their tokens; rotated token persisted before return; refresh started before
  sign-out does not resurrect the account; a late refresh failure does not delete a
  newer sign-in; a login that finishes after sign-out or import is dropped; an
  invalid refreshed credential (HTTP 200 `{}`) keeps the old record; error-policy
  cases built from pi-ai's real error messages.

### 3. Login orchestration — `src/background/account-login.js` + service worker

- `startAccountLogin(provider, { post })` creates an attempt `{ id, provider, phase,
  deviceCode?, verificationUrl?, needsCode }`, builds the `AuthInteraction`:
  - `select` is answered automatically: `device_code` for ChatGPT, `copy_code` for Claude.
  - `auth_url` events: the worker opens the URL in a new active tab; the panel gets
    `{ type: 'auth-event', provider, attemptId, kind: 'opened' }` — never the URL.
  - `device_code` events: the panel gets the user code and the verification URL
    (these are not secrets); the worker opens the verification URL.
  - `manual_code` / `text` prompts: phase becomes `awaiting-code`; resolved by
    `submitAccountInput(provider, attemptId, value)`; `cancelAccountLogin` rejects.
  - Keep-alive for the attempt's lifetime. On success `storeCredential(..., { attemptId })`
    and `auth-success { provider }` is posted; on failure the attempt's phase becomes
    `failed` with a safe message, and `auth-error` is posted.
- The panel's storage listener (`panel.js` around line 1002, today watching
  `changes.chatgptAuth`) watches the three `accountAuth.*` keys, so status, the code
  prompt and the model list update after an asynchronous login even if the
  `auth-success` message was missed.
- `accountLoginState(provider)` returns the current attempt without secrets. The
  panel calls it on open and after reconnecting, so a pending code prompt or device
  code is shown again, and an attempt the worker lost (no attempt in memory while
  the panel thought one was running) is shown as "sign-in was interrupted — start again".
- Service worker routes: `auth-status` (account status + login state), `auth-start`,
  `auth-cancel`, `auth-input`, `auth-logout` take `msg.provider` (default `'chatgpt'`).
  `auth-import` stays ChatGPT-only and stores the new shape through the queue.
- `chatgpt-auth.js` keeps only the `auth.json` import and a `getValidAuth()` adapter
  returning `{ accessToken, accountId }` from `getValidCredential('chatgpt')` for
  `chatgpt.js`; the hand-written device flow is deleted. `test/chatgpt.test.js` is
  updated: the device-flow test now drives `openaiCodexOAuth` from the vendor bundle
  through `startAccountLogin` with a faked `fetch` (including `expires_in`).
- Refresh triggered by `list-models`, `provider-test` or a task keeps the worker alive
  until it stores (same keep-alive helper).
- `installHeaderRules`: Origin removal for `||platform.claude.com/`, `||claude.ai/`,
  `||auth.x.ai/`; `user-agent: claude-cli/2.1.280` set for `||api.anthropic.com/`
  (Chrome drops a `User-Agent` set in `fetch`); `removeRuleIds` covers every id.
- `storage.onChanged` backup trigger watches the three `accountAuth.*` keys.
- `test/account-login.test.js`: select auto-answer per provider; manual code
  round-trip; cancel; state after a lost attempt; nothing posted contains a token,
  code, or a URL with a `state`/`code_challenge` query (assert on query strings).

### 4. Claude provider — `src/providers/anthropic.js`

- `AnthropicSession({ auth, apiKey, model, effort, systemPrompt, tools, notify })`,
  same interface and retry/abort/idle behaviour as `CompatibleSession`
  (`withRetry`, `readSse`, `MODEL_IDLE_MS`), images as base64 `image` blocks,
  tool results as `tool_result` blocks, notebook trimming as `chatgpt.js` does.
- **History**: each assistant turn is stored as the full content array in stream
  order — `thinking` (with `signature`), `redacted_thinking` (opaque `data`), `text`,
  `tool_use` — and sent back unchanged on the next request.
- **Completion rules**: a turn counts only after `message_stop`. An `error` event or
  a stream that ends without `message_stop` throws a provider error (so
  FallbackSession can take over, after a `text-reset` event if text was streamed).
  A `tool_use` whose accumulated JSON does not parse is not executed: it throws.
  `stop_reason: 'max_tokens'` with no complete tool call throws "the reply hit the
  output limit"; with complete tool calls they are returned.
- Headers per the spec, values in one exported constant `CLAUDE_CODE_IDENTITY`
  (`version: '2.1.280'`, betas `claude-code-20250219,oauth-2025-04-20`, system line
  `You are Claude Code, Anthropic's official CLI for Claude.`). Account mode gets the
  token from `getValidCredential('claude')` and retries once with `forceRefresh` on 401.
- **Thinking per model** (as pi-ai `api/anthropic-messages.js:935-975`): a small
  capability table keyed by model-id pattern. Adaptive models (Opus 4.6+, Sonnet 4.6+,
  and newer families): `thinking: { type: 'adaptive' }` plus
  `output_config: { effort }`; budget models: `thinking: { type: 'enabled',
  budget_tokens }` (low 2048, medium 8192, high 16384); off → `{ type: 'disabled' }`
  only where the model allows it. `max_tokens` stays above the budget. The effort
  list offered in the UI comes from the same table.
- `listAnthropicModels({ auth, apiKey })` from `GET /v1/models`.
- `test/anthropic.test.js`: request headers/body for both modes (identity block first
  in account mode only); adaptive vs budget thinking; SSE parsing of text, thinking
  with `signature_delta`, `tool_use` with streamed JSON; a two-request round trip
  (thinking + tool_use, then tool_result) sends the signed blocks back unchanged;
  missing `message_stop`, in-stream `error`, broken tool JSON, `max_tokens`;
  401 → refresh → retry.

### 8. Backup

- `backup.js`: `VERSION` 2 exports the credentials of the signed-in providers only
  (`accounts: { chatgpt?, claude?, grok? }`, credential objects without the local
  `generation`). Import accepts version 1 and 2 and normalises both first: version 1
  `chatgptAuth` becomes `accounts.chatgpt` **only when it is a non-null record** —
  `null` or missing means absent. Then it **merges per provider**: a provider present
  in the file replaces the local record (through its queue, bumping the generation);
  a provider absent from the file leaves the local record alone. There are no
  tombstones: a backup never signs a provider out.
- `drive-backup.js`: the fingerprint (around line 53) hashes settings and the
  normalised credential contents, **excluding `generation`**, so a token refresh
  triggers an upload and an unchanged restore does not; the fresh-install check
  (around line 100) counts any account record as existing state; the restore state
  (around line 115-118) is built in the new shape.
- Tests: v1 import with a record and with `null` (local account kept); v2 import;
  per-provider merge; fingerprint changes on refresh and not on restore;
  fresh-install detection with only a Claude record.
